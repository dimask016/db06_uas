Indexing Cerdas

Pada skala jutaan baris, full table scan mematikan performa. Strategi nyata:

  • ✅ Composite index pada kolom WHERE / ORDER BY (contoh: product, location_id, tanggal).
  • ✅ Covering index hindari回表 (MySQL/PostgreSQL).
  • ✅ PostgreSQL CREATE INDEX CONCURRENTLY tanpa downtime.
  • ✅ Gunakan EXPLAIN ANALYZE mendeteksi seq scan liar.
Contoh index strategis:
CREATE INDEX idx_inventory_location ON Inventory(location_id, product_id);
CREATE INDEX CONCURRENTLY idx_shipment_status ON Shipment(status, tanggal_kirim);

Backup & Point‑in‑Time Recovery

Bukan hanya backup, tapi recoverability. Pendekatan modern:

  • ✅ Full + incremental backup setiap 6 jam.
  • ✅ Archive WAL (PostgreSQL) atau binlog (MySQL) untuk PITR.
  • ✅ Replikasi silang region untuk disaster recovery.
  • ✅ Otomatisasi restorasi mingguan untuk validasi backup.

💡 real‑world: Backup + slave replicasi = RPO mendekati nol.

Optimasi Query & Connection Pool

  • ✅ Hindari N+1 query, gunakan join efisien atau batch.
  • ✅ PgBouncer / ProxySQL untuk pooling koneksi.
  • ✅ Partisi tabel (range partitioning) pada movement log.
  • ✅ Materized view untuk laporan berat.
-- Query dioptimasi dengan index & read replica
SELECT p.nama_produk, SUM(sm.jumlah)
FROM StockMovement sm JOIN Product p ON p.id = sm.product_id
WHERE sm.tanggal > NOW() - INTERVAL '30 days'
GROUP BY p.id;

Infrastruktur Database & Cache Layer

Untuk memenuhi skala ≥1 juta user, infrastruktur dapat bersifat on‑premise, cloud (DBaaS), atau hybrid. Pendekatan yang direkomendasikan:

  • ✅ Cluster database (1 master + minimal 3 slave) dengan replikasi real‑time dan failover otomatis.
  • ✅ Pemisahan beban baca (slave) dan tulis (master).
  • ✅ Redis Cluster sebagai caching layer untuk mempercepat query yang sering diakses (session, lookup data master, ringkasan stok).
  • ✅ Desain hybrid: SQL transaksional (ACID) untuk inventory & logistik, didukung Redis untuk mengurangi tekanan ke database utama.
  • ✅ Opsi cloud seperti Amazon RDS/Aurora, Google Cloud SQL, atau Azure Database for MySQL/PostgreSQL menyediakan read replica hingga 15 node, scaling otomatis, dan managed cache (ElastiCache).
Contoh penggunaan Redis caching:
GET /api/stock/:product_id → cek cache Redis → jika ada, langsung balik. Jika tidak, query ke slave database, simpan hasil ke Redis (TTL 60 detik).

Best practice dunia nyata: Kombinasi cluster database + Redis mampu menaikkan throughput query hingga 10x lipat untuk workload read‑heavy.

⚙️ Bagaimana failover bekerja: Jika master terdeteksi gagal, load balancer / orchestrator (HAProxy + Keepalived, atau managed cloud) secara otomatis mempromosikan salah satu slave menjadi master baru. Seluruh query SELECT diarahkan ke slave lainnya, sementara aplikasi hanya perlu mengubah endpoint write (atau via proxy transparan). Replikasi real‑time menjamin data loss minimal (semi‑sync menjamin setidaknya 1 slave menerima commit).

Keuntungan arsitektur ini

  • 📈 Horizontal read scaling – titik baca load tersebar ke 3 slave.
  • 🔄 High availability – failover otomatis tanpa intervensi manual.
  • 💾 Replikasi real‑time: master dan slave sinkron dalam hitungan milidetik.
  • ⚡ Maintenance tanpa downtime: upgrade slave, lalu promosikan.

Beban query terdistribusi

Load Balancer (Layer-4/7) mendeteksi tiap permintaan: INSERT/UPDATE/DELETE → master, SELECT → slave pool. Atau aplikasi config read/write splitting.

Contoh koneksi aplikasi (Spring / Laravel / Golang):
write_db -> master_host
read_db -> slave1_host, slave2_host, slave3_host (round‑robin)

Insight dunia nyata

Ratusan perusahaan skala besar menggunakan replikasi master‑slave + Redis untuk memisahkan beban baca. Dalam sistem inventory & logistik, laporan berat dan lookup stok sering di‑cache, sehingga query tidak perlu menyentuh database setiap saat.

Pada workload 1 juta user aktif harian: master menangani ~2k–5k write TPS, slave melayani ribuan read query, dan Redis mengurangi beban hingga 80% untuk endpoint populer.

🔁 Replikasi real‑time + Cache: Data yang berubah di invalidate dari Redis sehingga konsistensi tetap terjaga.

Contoh Query & Optimasi Nyata pada Struktur Database

📦 Query stok cepat dengan covering index

-- Mengambil stok per produk & lokasi (millions baris)
SELECT product_id, location_id, quantity
FROM Inventory
WHERE location_id = 101 AND quantity > 0;
-- Index : (location_id, product_id, quantity)
-- Membaca langsung dari index → tanpa back to table.

🚚 Laporan shipment harian menggunakan read replica

-- Query ini diarahkan ke SLAVE, tidak mengganggu transaksi PO
SELECT DATE(tanggal_kirim) as tgl, COUNT(*) as total_kirim
FROM Shipment
WHERE tanggal_kirim BETWEEN '2026-05-01' AND '2026-05-07'
GROUP BY DATE(tanggal_kirim);
Rekomendasi real‑time indexing untuk tabel Inventory & StockMovement: karena sering difilter berdasarkan `location_id`, `product_id`, `tanggal`, buat composite index (location_id, product_id, tanggal DESC) untuk mempercepat agregasi stok historis.
Alasan Desain Skalabilitas (Real‑World Reasoning)

Mengapa Master + 3 Slave + Redis?

▪️ Redundansi: jika satu slave gagal, masih ada dua untuk membaca.
▪️ Analytics terpisah: satu slave dedicated untuk laporan BI berat.
▪️ Failover deterministic: dengan 3 slave, quorum lebih mudah dicapai, menghindari split‑brain.
▪️ Redis cache: menyimpan hasil agregasi, session, dan data panas. Akses sub‑milidetik.
▪️ Scalability horizon: bisa menambah read replica hingga >10 dan Redis cluster terdistribusi.

Backup & Point‑in‑Time di Arsitektur Cluster

Backup diambil dari salah satu slave → tanpa beban ke master. WAL archiving tetap berjalan. Untuk DR antar region, kita bisa mereplikasi salah satu slave ke cloud secondary region dengan streaming replication.
Kombinasi on‑prem + cloud + Redis paling tangguh menghadapi ledakan user (≥ 1 juta).

Kesimpulan World‑Class: Arsitektur yang diusulkan (1 master + 3 slave + replikasi real‑time + Redis cluster) adalah fondasi database yang telah terbukti pada platform dengan traffic 1 juta+ user (e‑commerce, logistik, fintech). Indexing dan optimasi query menyempurnakan IO, backup & failover automation menjamin kontinuitas bisnis. Untuk melampaui level enterprise, dapat ditambahkan sharding horizontal di kemudian hari atau migrasi ke distributed SQL (CockroachDB, TiDB) tanpa merubah logika aplikasi secara drastis.
